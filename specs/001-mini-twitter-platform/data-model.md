# Data Model: SocialMedia Platform

**Date**: 2026-07-18  
**Source**: [spec.md](./spec.md) and [plan.md](./plan.md)

## Modeling rules

- PostgreSQL `uuid` stores all identifiers. Externally referenced records and events are
  generated by their owning application as UUIDv7.
- Timestamps are UTC `timestamptz` with microsecond precision.
- A database contains only its owner's tables. Cross-service IDs are scalar UUID values, never
  cross-database foreign keys or ORM relationships.
- Each service has one Flyway `V1` migration and `ddl-auto=validate`.
- Lombok is an implementation-only annotation processor. JPA entities may use targeted getters,
  setters, and a protected no-argument constructor, but never entity-wide `@Data`, generated
  `toString`, or mutable-field `equals`/`hashCode`; these rules do not alter the schemas below.
- Reverse-chronological indexes end with UUIDv7 `id` as a deterministic tie-breaker.
- Table/column names below are descriptive; implementation may use snake_case without changing
  the contract.

## User database (`user_db`)

### Account

| Field | Type | Rules |
|---|---|---|
| `id` | UUIDv7 | Primary key; generated by User Service |
| `email` | string | 3-254 characters; valid email; private |
| `normalizedEmail` | string | `trim + lowercase(Locale.ROOT)`; unique |
| `username` | string | 3-30 characters; `[A-Za-z0-9_]+`; immutable |
| `normalizedUsername` | string | lowercase username; unique |
| `displayName` | string | trimmed, 1-80 Unicode code points |
| `bio` | string | trimmed, 0-160 Unicode code points |
| `passwordHash` | string | BCrypt only; never returned or logged |
| `createdAt` | timestamp | Set once |

Indexes/constraints:

- Unique `normalizedEmail`.
- Unique `normalizedUsername`.

Validation notes:

- Registration is one transaction, so a uniqueness failure creates no partial profile.
- Password input is 12-72 UTF-8 bytes before hashing. The raw password is never retained after
  the request.
- There is no separate Profile row: public fields share the account lifecycle.
- There is no account-status, refresh-token, session, credential-history, or count column.
  Those have no baseline transition and are marked **SIMPLIFY**.

State transition:

```text
ABSENT --register--> ACTIVE ACCOUNT
```

Account deletion, disabling, profile editing, and password recovery have no baseline transition.

## Post database (`post_db`)

### Post

| Field | Type | Rules |
|---|---|---|
| `id` | UUIDv7 | Primary key; generated by Post Service |
| `authorId` | UUID | JWT subject; immutable; no cross-database FK |
| `text` | string | Exact submitted text; non-blank; 1-280 Unicode code points |
| `publishedAt` | timestamp | Immutable sort time |
| `parentPostId` | UUID, nullable | Same-database parent; null means original post |
| `parentAuthorId` | UUID, nullable | Snapshot of the parent's author for reply notification |
| `deletedAt` | timestamp, nullable | Null while visible; author-only transition |

Indexes/constraints:

- Index `(authorId, publishedAt DESC, id DESC)` for profile-post keysets.
- Index `parentPostId` for parent availability/direct-reply inspection.
- Check: `parentPostId` and `parentAuthorId` are both null or both non-null.
- Parent uses a same-database FK with `ON DELETE RESTRICT`; rows are soft-deleted, so replies
  remain.

State transition:

```text
ABSENT --publish/reply--> VISIBLE --author delete--> DELETED
```

- No edit transition exists.
- A reply requires a visible parent at creation time.
- Deleting a parent does not change its reply rows. A reply response reports parent availability
  from the parent row's `deletedAt`.
- Deleted posts reject likes and replies and are omitted from direct/list/bulk reads.

### PostLike

| Field | Type | Rules |
|---|---|---|
| `id` | UUIDv7 | Primary key; generated by Post Service |
| `postId` | UUID | Same-database FK to Post |
| `userId` | UUID | JWT subject; no cross-database FK |
| `createdAt` | timestamp | Set once |

Indexes/constraints:

- Unique `(postId,userId)` makes `PUT .../likes/me` idempotent.
- Index `postId` supports visible like count.
- Like rows are retained when a post is soft-deleted; they are simply no longer exposed.

State transition:

```text
ABSENT --like--> PRESENT --repeat like--> PRESENT
```

Unlike is out of scope.

### Post OutboxEvent

| Field | Type | Rules |
|---|---|---|
| `eventId` | UUIDv7 | Primary key and Kafka envelope identity |
| `aggregateId` | UUID | Post ID |
| `eventType` | string | `post.published.v1` or `post.deleted.v1` |
| `schemaVersion` | integer | `1` |
| `topic` | string | `post-events.v1` |
| `messageKey` | string | Post ID |
| `payload` | JSONB | Contract payload only; no entity serialization |
| `occurredAt` | timestamp | Domain-change time |
| `correlationId` | string | Propagated request correlation value |
| `status` | enum | `PENDING`, `PUBLISHED`, `FAILED` |
| `attemptCount` | integer | Starts at 0; max automatic attempt 10 |
| `nextAttemptAt` | timestamp | Next eligible publish time |
| `publishedAt` | timestamp, nullable | Set after Kafka acknowledgement |
| `lastError` | string, nullable | Sanitized and truncated; no payload/secrets |
| `createdAt` | timestamp | Row creation time |

Indexes/constraints:

- Index `(status,nextAttemptAt,createdAt)` for polling.
- A reply creates one `post.published.v1` event whose parent fields let Timeline and Notification
  apply their own behavior; no second reply-specific outbox event is required.

State transition:

```text
PENDING --ack--> PUBLISHED
PENDING --failure/attempt<10--> PENDING(nextAttemptAt)
PENDING --failure/attempt=10--> FAILED
FAILED --manual requeue--> PENDING
```

Published rows are retained 7 days; failed rows 30 days; pending rows are not age-purged.

## Follow database (`follow_db`)

### FollowRelationship

| Field | Type | Rules |
|---|---|---|
| `id` | UUIDv7 | Primary key; new ID for each new follow period |
| `followerId` | UUID | JWT subject |
| `followedId` | UUID | Target verified through User Service |
| `followedAt` | timestamp | Eligibility start time |

Indexes/constraints:

- Unique `(followerId,followedId)` while the row exists.
- Check `followerId <> followedId`.
- Index `(followedId, followedAt, followerId)` for eligible-follower keysets/count.
- Index `followerId` for following count.

State transition:

```text
ABSENT --follow--> PRESENT --repeat follow--> PRESENT
PRESENT --unfollow--> ABSENT --repeat unfollow--> ABSENT
ABSENT --re-follow--> PRESENT(new id, new followedAt)
```

Only real absent/present transitions write events. Physical deletion is sufficient because the
outbox preserves the unfollow fact and timestamp.

### Follow OutboxEvent

Same fields and lifecycle as Post OutboxEvent, with these values:

- `aggregateId`: relationship ID.
- `eventType`: `follow.created.v1` or `follow.removed.v1`.
- `topic`: `follow-events.v1`.
- `messageKey`: `followerId:followedId`.
- Removed-event payload includes `unfollowedAt` so Timeline cleanup is time-bounded across a
  later re-follow.

The table is duplicated in Follow rather than imported from a shared outbox module because each
producer owns its transaction and schema.

## Timeline database (`timeline_db`)

### TimelineEntry

| Field | Type | Rules |
|---|---|---|
| `id` | UUIDv7 | Primary key; generated by Timeline Service |
| `ownerUserId` | UUID | User whose home timeline owns the reference |
| `postId` | UUID | Post-owned reference |
| `authorId` | UUID | Used only for unfollow cleanup |
| `publishedAt` | timestamp | Post-owned ordering value copied into derived reference |
| `sourceEventId` | UUID | Originating `post.published.v1` identity |
| `createdAt` | timestamp | Fan-out materialization time |

Indexes/constraints:

- Unique `(ownerUserId,postId)` is the primary idempotency rule.
- Index `(ownerUserId,publishedAt DESC,postId DESC)` supports home cursor reads.
- Index `(ownerUserId,authorId,publishedAt)` supports bounded unfollow cleanup.
- `sourceEventId` is not globally unique because one publication creates one row per follower.

State transitions:

```text
ABSENT --post event + eligible follow--> PRESENT
PRESENT --duplicate event--> PRESENT
PRESENT --post deleted event--> ABSENT
PRESENT --follow removed and publishedAt<=unfollowedAt--> ABSENT
```

There is no copied post text, reply state, username, like count, follow projection, fan-out job,
or processed-event table. Inserts and deletes are already idempotent through the domain key.

## Notification database (`notification_db`)

### Notification

| Field | Type | Rules |
|---|---|---|
| `id` | UUIDv7 | Primary key; generated by Notification Service |
| `recipientUserId` | UUID | Query owner |
| `actorUserId` | UUID | Follower or reply author |
| `type` | enum | `FOLLOW` or `REPLY` |
| `subjectId` | UUID | Relationship ID for FOLLOW; reply post ID for REPLY |
| `parentPostId` | UUID, nullable | Present only for REPLY |
| `eventTime` | timestamp | Source event occurrence time; collection sort time |
| `sourceEventId` | UUID | Kafka event identity; unique |
| `availableAt` | timestamp | Time the visible row committed |

Indexes/constraints:

- Unique `sourceEventId` prevents a second visible row.
- Index `(recipientUserId,eventTime DESC,id DESC)` supports notification keysets.
- Check: FOLLOW has null `parentPostId`; REPLY has non-null `parentPostId`.
- Actor equal to recipient is consumed and recorded but does not create a visible notification.

State transition:

```text
ABSENT --first relevant event--> VISIBLE
VISIBLE --duplicate/replay--> VISIBLE
```

Persistence plus `availableAt` is the delivery state. Read/unread, templates, channels, retry
status, and external delivery state machines are **SIMPLIFY** because retrieval is the only
delivery mechanism.

### ProcessedEvent

| Field | Type | Rules |
|---|---|---|
| `eventId` | UUID | Event identity |
| `consumerName` | string | `notification-service-v1` |
| `eventType` | string | Known source type |
| `processedAt` | timestamp | Commit time |

Indexes/constraints:

- Composite primary key `(consumerName,eventId)`.
- Inserted in the same transaction as Notification, including for a valid self-notification
  that intentionally creates no visible row.

## Outbox/event payload field mapping

| Event | Payload fields |
|---|---|
| `post.published.v1` | `postId`, `authorId`, `publishedAt`, `parentPostId?`, `parentAuthorId?` |
| `post.deleted.v1` | `postId`, `authorId`, `deletedAt` |
| `follow.created.v1` | `relationshipId`, `followerId`, `followedId`, `followedAt` |
| `follow.removed.v1` | `relationshipId`, `followerId`, `followedId`, `unfollowedAt` |

Every envelope also carries `eventId`, `eventType`, `schemaVersion`, `aggregateId`,
`occurredAt`, and `correlationId`. It never carries a password, JWT, email, or internal entity
serialization.

## Cursor model

The client treats the cursor as opaque. The decoded version-1 structure contains only:

| Field | Purpose |
|---|---|
| `v` | Cursor format version; must equal 1 |
| `sortTime` | Exclusive upper bound for the next page |
| `id` | UUIDv7 tie-breaker |

The server orders by `sortTime DESC, id DESC` and queries values strictly less than the cursor
tuple. A malformed cursor, invalid timestamp/UUID, or unsupported version returns `400` without
querying data.
